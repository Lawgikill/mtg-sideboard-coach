# MTG Sideboard Coach

A personal Magic: The Gathering sideboard planning tool for Standard-legal decks. Built as both a web app (Vite) and a Windows desktop app (Electron).

## Tech Stack

- **React 19 + TypeScript** via Vite
- **Electron** for the Windows desktop build — a per-user NSIS installer that updates itself from GitHub Releases via **electron-updater**
- **@dnd-kit** for drag-and-drop
- **lucide-react** for icons, **mana-font** for MTG mana symbols
- Data persisted in `localStorage`; Electron also writes hourly backup files to disk

## Key Commands

```bash
npm run dev          # Start Vite dev server
npm run desktop      # Build + launch Electron app locally
npm run package:win  # Build the Windows installer → release/ (never publishes)
npm run lint         # ESLint
```

## Versioning

**1.0.0 is the first release.** The version was reset from 3.2.0 on 2026-10-21, so any other version number that turns up — old portable builds in `release/` (`v3.1.0`, `v3.2.0`), the `v1.5.0` in an old handoff note — comes from **before** the reset and is not part of this sequence. Those are all older than `v1.0.0` despite being numerically higher. Release notes start at 1.0.0 in `CHANGELOG.md`.

**The `v1.0.0` tag was moved once, deliberately.** It was first pushed at `23a0c27`, before the installer existed, then re-pointed forward to the commit that added the installer and self-update, so that 1.0.0 is the first version anyone can install. That was the owner's explicit choice after the history implications were raised. Only the tag moved: no commits were rewritten, and `main` simply gained a commit. Never move a release tag once a Release with an installer has been published for it — installed copies compare against those versions.

`package.json` is the only source of the version. The app reads it at runtime through `app.getVersion()` (the home screen shows it, and the updater compares against it), and electron-builder uses it to name the installer `mtg-sideboard-coach-setup-<version>.exe` and to write `latest.yml`. Bump with `npm version <x.y.z> --no-git-tag-version` so `package-lock.json` follows — before the reset the lockfile had drifted to `2.12.0` while `package.json` said `3.2.0`, because only one of them was being edited by hand. Do not search-and-replace version strings in the lockfile: unrelated dependencies (`boolean`, `escalade`) are themselves at `3.2.0`.

## Data Model

- **`Deck`** — name, color identity (`colors` + optional `splashColors`), `DeckEntry[]` (main + sideboard), `Matchup[]`
- **`Matchup`** — shared globally across all decks (add once, synced to every deck automatically via `syncGlobalMatchups`). Each deck stores its own notes/plan per matchup.
- **`PlanEntry`** — a card going `in` (from sideboard) or `out` (from main) for a given matchup
- **`SituationalSection`** — optional secondary plan within a matchup (e.g. on the play vs. on the draw)
- **`CardDatabase`** — Standard-legal cards synced from Scryfall's oracle bulk endpoint, stored in `localStorage`. `CardRecord` includes `power` and `toughness` (strings, optional — creatures only), `loyalty` (string, optional — planeswalkers only), and `faces` (optional `CardFace[]` for double-faced cards — each face has its own `name`, `typeLine`, `oracleText`, `manaCost`, `power`, `toughness`, `loyalty`). Oracle text is expanded with reminder text for evergreen keyword abilities (Flying, Haste, etc.) during sync via `expandKeywordReminders` in `scryfall.ts`.
- **`Matchup`** — also stores `splashColors?: MtgColor[]` (inferred from the opponent decklist, globally synced) and `opponentEntries?: DeckEntry[]`, a globally-synced opponent decklist for the matchup. Set once via the Opponent Deck panel in the plan editor; propagated to all decks via `updateGlobalMatchup`. Also stores `opponentVariantEntries?: DeckEntry[]` — cards seen in actual play, used to compute net "Also Seen" delta entries.

- **`Deck.replayOpponents`** — `{ [matchID]: matchupName }`, which archetype the opponent was playing in a given parsed MTGA match. Stores the matchup **name**, not its id, matching how the journal records an opponent: a matchup later renamed or deleted leaves the record readable instead of dangling.

## Match Journal

Each deck has a **Journal** tab (alongside Plans) for logging match results:
- **`MatchLog`** — opponent name, date, and a list of `GameLog` entries
- **`GameLog`** — result (`win` / `loss` / `draw` / `''`), an optional `start` (`play` / `draw`), and a notes field
- Win/loss record (e.g. `2-1`) is computed from game results and displayed as a badge
- Matches are stored newest-first in `deck.matchLogs`
- Persisted automatically via the existing `onUpdateDeck` → `saveDecks` flow
- **`Deck.journalNotes`** — free-form, match-unspecific notes shown at the top of the tab

## Key Behaviors

- **Global matchups**: matchups are defined once and propagated to all decks. Renaming or deleting a matchup affects every deck.
- **Color identity + splash detection**: `inferDeckColorProfile` in `arena.ts` returns `{ colors, splash }`. It counts colored mana **pips** (weighted by copies) rather than cards, since pip count reflects real color commitment — 4× `{B}{B}{B}` is a heavier commitment than 4× `{2}{B}`. A color is a splash when its share of total colored pips is under 15%, **or** it appears in ≤2 distinct cards and is under 25% (catches the single-card splash, e.g. 4× Leyline Binding). Guards: hybrid symbols split weight across their colors (`{R/W}` = 0.5 each); decks under 10 total pips skip detection; if every color qualifies as a splash the result is discarded. Every card face counts toward color identity (unlike type grouping and mana-value sorting, which use the front face) — Scryfall only gives a back face a mana cost when that face is castable, so uncastable transform backs contribute no pips automatically.
- **Splash rendering**: `ManaPips` takes an optional `splash` prop. Splash pips render smaller (11px vs 17px) with reduced opacity and are **ordered last**, after the main colors; WUBRG order is preserved within each group. Screen-reader labels mark them "(splash)".
- **Matchup color identity**: inferred from the opponent decklist on import and on any "Also Seen" import, via `inferOpponentColorProfile`. Uses the **net** Also Seen delta so cards already in the conventional 75 aren't double-counted. Manual pip clicks override the inferred value — toggling a color on makes it a main color, toggling one off drops its splash marking. Nothing recomputes until the next import.
- **Opponent card filter**: a "Filter by opponent card…" autocomplete input below the color filter in the Matchups panel lets you add card chips (art thumbnail + name + × to remove). The matchup list filters to only show matchups whose opponent decklist contains ALL chipped cards (AND logic). When a filtered matchup is open, matching rows in the Opponent Deck panel are highlighted green. Filter state lives in `DeckWorkspace` as `opponentFilterCards: CardRecord[]`.
- **Opponent deck**: each matchup has an optional `opponentEntries` field storing the opponent's decklist (parsed via Arena importer). Set from the collapsible "Opponent Deck" panel in `PlanEditor` (appears above Notes). Synced globally so all decks see the same opponent list for a given matchup. The opponent's main deck is grouped by card type (same priority order as the player's Main zone, including front-face priority for DFCs); basics sort first within the Land section; each section header shows the card count. The opponent's sideboard stays flat.
- **Plan normalization**: `normalizePlanEntries` deduplicates and caps plan quantities against the actual deck entries. Called whenever the deck or plan changes.
- **Scryfall sync**: reads the bulk-data index, then downloads the `oracle_cards` entry's `jsonl_download_uri` — a **gzip-compressed JSONL** file (~24MB compressed, ~200MB decompressed, ~38k cards). Filters for `lang === 'en'` and `legalities.standard === 'legal'` (~4.9k cards). Progress streamed via callback.
  - **Electron path**: the renderer calls `electronAPI.fetchScryfallCards(url)`; the main process downloads via Node `https` (following redirects to `data.scryfall.io`), gunzips, parses the JSONL, and pre-filters to Standard-legal English cards before returning — the decompressed file is far too large to pass across IPC intact.
  - **Web path**: streams the response with byte progress, then decompresses in-browser via `DecompressionStream('gzip')`. Scryfall serves the `.gz` without a `content-encoding` header, so the browser does not decompress it automatically.
  - Network fetches retry 3× with a 3s delay; each failure mode (DNS/connection, HTTP status, parse, mid-stream drop) throws a distinct message so the cause is identifiable from the UI.
- **Tokens are synced too** (`isArenaToken` in `scryfall.ts`). Every token is `legalities.standard === "not_legal"`, so the legality filter dropped all of them — which is why a Treasure on the battlefield had no hover preview while every real card did. Every token with `layout` of `token`/`double_faced_token` is kept — about **1,006** against 5,164 cards. Previews need no change at all, since they are a name lookup.
  - **Tokens are also indexed under their own keys** (`tokenKey`), because the plain name goes to the real card. See the Replay narration rules for why a token line needs them.
  - **Name collisions are decided by `claim()` in `createCardIndexes`, on two rules in order.** A real card beats a token (`CardRecord.isToken`), since Treasure, Clue and every creature-type token share names with real cards and a decklist entry always means the card. Then a card whose *own* name is the key beats one matching only through a face — without that, `Treasure` resolved to the double-faced **Vampire // Treasure** token and the hover showed a Vampire beside the Treasure. Ties keep the incumbent, so the result does not depend on iteration order.
  - **The filter exists twice and both copies must agree.** `electron/main.cjs` pre-filters the bulk data in the main process before handing it to the renderer, so a filter loosened only in `scryfall.ts` changes nothing on the desktop build — the renderer never sees what main already dropped. Tokens were added to the renderer first and the synced count did not move by a single card.
  - **Do not try to narrow this to Arena tokens.** It was tried and fails: `games` is a per-*printing* field, and `oracle_cards` keeps one printing per oracle id. Measured against the real bulk file, it picked a paper-only printing of Treasure (`games: ["paper"]`), so the filter matched **24 of 1,006** tokens and excluded the exact one that prompted the feature. The API reports `games: ["paper","mtgo","arena"]` for Treasure, so checking there is misleading — only the bulk file matters.
- **Delete all decks**: trash button beside the "Decks" heading on the home screen (only shown when decks exist) clears every deck; requires a `confirm()` prompt.
- **Arena name aliases**: `ARENA_NAME_ALIASES` in `scryfall.ts` maps MTG Arena export names (OM1 set) to their Scryfall oracle names (SPM Marvel set).
- **Main deck type grouping**: the Main deck `CardZone` groups cards into sections by type — Creature, Artifact, Enchantment, Planeswalker, Instant, Sorcery, Land. Multi-type cards use priority order (Creature wins over Artifact, etc.). Double-faced cards use the front face `typeLine` for grouping (`faces[0].typeLine` when available) and the front face mana cost for sort order. Basic lands sort first within the Land section. Each section header shows the total card count. Uses `getTypeGroup()` + `TYPE_GROUPS` constant in `App.tsx`.
- **Ordering is shared between display and export**: `groupEntriesByType()` in `App.tsx` is the single source of truth — sorts by mana value then name (`compareCardEntries`), buckets into `TYPE_GROUPS`, and puts basics first among lands. It backs the Main zone, the opponent main deck, **and** both clipboard exports, so what you copy always matches what's on screen. `sortEntriesForExport()` wraps it for exports: main grouped by type, sideboard flat by mana value. Without it, exports came out in raw insertion order (the order the list was first pasted, later additions appended) — which looked random next to the sorted panels. `serializeArenaDecklist(deck, entries?)` in `arena.ts` takes the pre-sorted entries; the ordering lives in `App.tsx` because `arena.ts` can't import from it without a cycle.
- **Copy sideboard plan**: writes to **two destinations at once**. The in-app `copiedPlan` state keeps the full object (notes, primary plan, situational sections) for Paste, while the system clipboard gets readable text (`IN: 1 Erode; 1 Get Lost…` / `OUT: …`, cards sorted as the columns display them, situational sections appended as labelled blocks). Parsing text back on paste was the alternative and is strictly worse — text cannot carry notes or situational sections, so a paste would silently drop half the plan.
- **Copy plan from another deck**: a "Copy plan from…" dropdown appears in the Sideboard Plan header when other decks have a plan for the same matchup. Selecting a deck transplants its full plan (notes, primary In/Out entries, all situational sections) into the current deck's plan. Donor decks are computed in `PlanEditor` by filtering `allDecks` for decks with a matching matchup ID and at least one plan entry.
- **Opponent deck copy**: clipboard icon in the Opponent Deck header copies the opponent's decklist to the clipboard in Arena format (Main / Sideboard / Also Seen sections) when a deck is loaded, sorted via `sortEntriesForExport`.
- **Copy actions confirm**: a clipboard write gives no visible sign it worked, so every copy action reports briefly via the shared `useCopyFeedback` hook (one timer definition, so the duration cannot drift as more are added). A labelled button swaps its text to "Copied"; an icon-only button swaps its icon to a green check, since it has no label to change.
- **Arena decklist button**: the labelled toolbar action **copies** rather than downloads — pasting into Arena's importer is what the list is for — with the `.txt` download kept beside it as an icon-only button so nothing is lost.
- **Opponent deck is editable, not import-only**: `CardAddInput` autocompletes sit below the Main and Sideboard sections ("Add to main deck…" / "Add to sideboard…"), and rows carry the standard hover steppers. One input per zone because the same card legitimately appears in both at different counts, so `addOpponentCard` matches on name **and** zone. Steppers are not optional here: without them a mistyped add could only be undone by clearing the whole opponent deck. Both zone sections render whenever the panel is open, even when empty, since otherwise there is nowhere to put the first card. All edits route through `updateOpponentEntries`, so they sync globally and recompute matchup colors exactly as an import does.
- **Also Seen (variant entries)**: a second import section at the bottom of the Opponent Deck panel records cards seen in actual play. Net quantities are computed by subtracting each card's total count in the conventional 75 (main + sideboard combined); only cards with a positive delta are shown. Displayed in a 2-column **row-major grid** (`.also-seen-grid`) sorted by mana value — unlike the `column-count` newspaper flow used for the opponent's main deck and sideboard, which runs top-to-bottom within each column and makes a sorted list look shuffled when read across rows. Propagated globally alongside `opponentEntries` via `updateGlobalMatchup`. Three ways to add, all recomputing matchup colors:
  - **Import** merges rather than replaces, via `mergeVariantEntries` — it keeps the **highest count seen per card, not the sum** (spotting 2 Duress across three games means the deck runs 2, not 6). Merging can raise a count but never lower it; use the row `×` or the clear button to correct an overcount.
  - **Single-card add** (`addVariantCard`) via the autocomplete below the list. Counts are stored raw and displayed net, so adding a card already in the conventional 75 bumps it past that count — otherwise the first click would add nothing visible.
  - **Per-row steppers** correct a count in place, and stepping to zero drops the card — needed because a merging import can no longer be corrected by re-importing a fixed list.
- **Four-copy limit**: handled two different ways on purpose.
  - **Observational data is clamped**: the Opponent Deck's "Also Seen" caps at 4 on every entry path — screenshot OCR, text paste, single-card add, and the row steppers — because OCR noise is the real source of impossible counts (a tracker screenshot produced "Ashling x7" out of row chrome). The OCR review list clamps before display and disables `+` at the cap.
  - **Authoritative decklists are flagged, never rewritten**: the player's own deck and the opponent's imported 75 show a red banner naming the offenders (`findCopyLimitViolations` / `describeCopyViolations`) and tint the offending rows via `.card-row.copy-violation`. Silently clamping an import would hide the mistake instead of surfacing it.
  - **Counted by name across BOTH zones** — the limit is four per deck, not per zone, so 3 main plus 2 sideboard is already illegal and lights up in both lists. Neither row looks wrong alone, which is exactly why the cross-zone total is what gets checked.
  - **Exemptions** (`cardAllowsAnyNumber`): basic lands, detected via `typeLine.includes('Basic')` — these are the exception that actually matters, since every deck runs 20+ and you will routinely see five in one game; a blanket cap would silently corrupt them. Also cards whose own text says "any number of cards named" (Relentless Rats, Dragon's Approach). Both rules were verified against live Scryfall data, including snow basics (`Basic Snow Land — Island`).
  - `.card-row.copy-violation` carries two classes so it outranks the single-class green filter highlight on specificity, independent of declaration order.
- **One row control pattern everywhere**: every editable card row — Main, Sideboard, In/Out plan, Also Seen — renders the same `.entry-quantity` group of `−` / count / `+`, in that order, inside the **single `auto` grid cell** of `.card-row`. Keeping the group in one cell is the point: an earlier version gave each control its own grid column, which is what made controls wrap to a second implicit row and inflate the row height whenever one was added. The buttons are hidden until the row is hovered (or focused), driven by the one `.card-row:hover .entry-qty-btn` rule, so there is a single place to change that behaviour.
  - **No per-row delete control.** Stepping the count to zero removes the row in every one of these lists, so a trash button was pure redundancy sitting next to `+` — the only irreversible control in the group, adjacent to the one you press most, with no undo. `Trash2` is still used for real deletes: decks, matchups, matches, and clearing a whole list.
  - This replaced an earlier rule that put the count in the right-hand column with controls before it. That rule existed only to serve the per-control grid columns; it does not apply any more.
- **Sideboard Stats**: "Stats" button in the deck workspace toolbar opens a modal showing aggregate sideboarding data across all matchup plans for the deck. Two columns — Coming In (sideboard cards) and Going Out (main deck cards) — each sorted by total quantity descending. Each row shows card art thumbnail, name, total copies across all plans (primary + situational), and a badge for how many distinct matchups the card appears in.
- **Card hover previews**: `getPreviewPosition` treats its `placement` argument as a *preference*. If the preferred side lacks room it flips to the other side. Without this a row in a leftmost column anchored the preview off-screen, so it rendered but was never visible. The space needed is **measured per card** by `measurePreviewWidth`, not assumed: a double-faced card renders one image per face, so it needs ~586px against ~310px for a single face. Each row passes the `card` it already holds. Measuring a fixed single-card width instead let DFC previews pass the fit check and then clip at the right edge.
- **Drag-and-drop**: cards dragged from Main/Sideboard columns into the Sideboard Plan drop zones. Uses `DragOverlay` (portal-based) so the shadow is never clipped by `overflow: hidden` containers.
- **Click-to-plan**: clicking a Main card adds it to the primary plan's Out column (and increments on repeat clicks, capped at deck quantity); clicking a Sideboard card adds/increments In. Clicking a card already in the In/Out plan columns decrements its quantity by 1 (auto-removed at 0) — mirrors the `−` button. Works alongside drag-and-drop since dnd-kit only starts a drag past an 8px pointer-move threshold.
- **Deck deletion**: done from the home screen deck card (hover to reveal the delete button); requires a `confirm()` prompt.
- **Clear sideboard plan**: eraser button in the Sideboard Plan header wipes notes, all In/Out entries, and all situational sections for the current matchup without deleting the matchup itself.
- **Delete all matchups**: trash button in the Matchups panel header (only visible when matchups exist) removes all matchups from every deck at once; requires a `confirm()` prompt.
- **Cards JSON export**: "Cards JSON" on the home screen exports the full ~5k Standard card database. "Filtered JSON" in the deck workspace exports only cards referenced across all decks and opponent decklists — same format, much smaller file.
- **Screenshot OCR import** (Electron only): the Opponent Deck importer accepts a pasted, dropped, or browsed screenshot of a tracker's opponent-deck list through the `useScreenshotOcr` hook, which owns the four-copy clamp. The hook had a second caller in Scout's capture panel; it stays a hook so the clamp is not reimplemented by the next importer that wants a screenshot.
  - **The Opponent Deck importer writes OCR results into its textarea** as decklist lines (`2 Dusk Rose Reliquary`) rather than opening a review list. The textarea then *is* the review step, the existing Arena parser still assigns zones from `Deck` / `Sideboard` headers, and results append — so two screenshots, or a screenshot plus a typed `Sideboard` header, build one list before importing. Lines that matched no card are reported as a count rather than silently dropped. OCR runs in the **main process** via `tesseract.js` (`ocr-image` IPC), keeping one worker alive across imports since startup costs a second or two.
  - **OCR alone is not accurate enough** — a real tracker screenshot produced "Pinnade starcage", "IN The mind stone", "By * | weapons Manufacturing 1". What makes it usable is `parseOcrLines` in `ocrParse.ts`, which fuzzy-matches each line against the ~4.9k card names from the synced database using bounded Levenshtein (early-exits once a row exceeds the cutoff), retrying each line with leading tokens dropped to shed art-thumbnail noise. Quantity is taken from a leading or trailing 1-2 digit number. Measured on a real screenshot at full database scale: 16/16 cards, correct quantities, no false positives, ~195ms.
  - **Two-column screenshots**: tesseract's own line grouping runs across the whole image and staples a left-column card onto a right-column one, which fuzzy matching cannot undo. `ocr-image` therefore returns word **bounding boxes**, and `linesFromWords` in `ocrLayout.ts` rebuilds the lines — splitting at vertical whitespace corridors, folding digit-only strips back into the column on their left (that is the quantity gutter; treating it as a column detaches every count from its card), then grouping each column into rows. Row tolerance is `0.65 × median` word height: swept against real screenshots, below 0.6 a quantity splits onto its own row and above 0.7 adjacent rows merge. Median, not per-word, because tall fragments of card art otherwise inflate it. Upscaling the image first was tried and reverted — 3x recovered a card on one screenshot but lost two on another.
  - **Split-name cards**: `buildOcrCandidates` makes each half of a `"Front // Back"` name matchable on its own, resolving to the parent card. This covers transform and modal DFCs, adventures, splits, and prepared spells (`Emeritus of Abundance // Regrowth`, layout `prepare`) — a tracker lists whichever half it saw, and the combined name is nothing like it. Results dedupe on the resolved card name keeping the **higher** quantity, so seeing both halves yields one row rather than counting the card twice. Without this, a back face fuzzy-matched to whatever unrelated full name was nearest (`Summon: Esper Maduin` landed on `Summon: Esper Ramuh`) and a front face fell below threshold entirely.
  - Results always land in a **review list** before anything is added: low-confidence rows carry a `?` flag showing the raw OCR text, unmatched lines are shown greyed, quantities are editable (digits are the least reliable thing OCR reads) and a row stepped to 0 is skipped on confirm. Never import OCR output directly.
  - **Packaging**: `eng.traineddata` (~5MB) ships in `build/traineddata` via `extraResources` so OCR works offline; without it tesseract downloads it from a CDN on first use. `tesseract.js-core` must be in `asarUnpack` — wasm will not load from inside an asar. **Do not filter `tesseract.js-core` builds out of `files`**: the variant is chosen at runtime by CPU feature detection (`relaxedSimd()` / `simd()` in `worker-script/node/getCore.js`), so the needed file differs per machine and per `oem` setting. Excluding the ones that looked unused shipped a build that died with `Cannot find module 'tesseract.js-core/tesseract-core-relaxedsimd'`. The whole ~44MB package ships.
- **Journal pop-out**: a Pop Out button opens the Journal in its own `BrowserWindow`, loading the same `index.html` with `#journal=<deckId>`; the renderer reads that hash on boot and renders standalone. Needed because `setWindowOpenHandler` denies `window.open()` and routes it to the OS shell. Re-requesting the same deck focuses the existing window. **Each window keeps its own React copy of the decks and writes the whole array to storage**, so whoever saves emits `decks-changed` and the main process broadcasts `decks-updated` to every other window, which re-reads storage — without this, a window holding stale state would silently clobber the other's edits on its next save. A `skipNextSave` ref stops a window writing back what it just read (it also suppresses the mount-time save, so launching no longer writes decks until something actually changes).
- **Journal opponent field**: a dropdown of the deck's matchup names, not free text. It stores the matchup **name**, not an id — that keeps pre-existing free-text entries valid with no migration and leaves the export untouched. Any value not in the current matchup list (legacy text, or a matchup since renamed or deleted) is still offered as an option tagged "(not a current matchup)" so selecting nothing can never silently drop history. Trade-off: renaming a matchup does not retroactively update journal entries.
- **Play/draw per game**: a dropdown beside each game's result. `GameLog.start` is **only stored once the player picks one** — left undefined, the displayed value is derived from the previous game via `inferGameStart` (whoever lost chooses who starts and all but always plays, so a win means you are on the draw next game, a loss means on the play). Deriving rather than writing a default at creation matters because results are often entered out of order: filling in game one's result after game two already exists would never trigger a stored default, but does update a derived one. An inferred value renders dimmed; an explicit pick is never overwritten. The blank option only appears where nothing can be inferred — game one, or when the previous game has no result.
- **General Notes** (Journal tab, directly below the toolbar): collapsible free-text for the deck, stored on `Deck.journalNotes`. Undefined falls through to `JOURNAL_NOTES_PROMPTS` (eight review questions) rather than writing them to storage, so opening the tab never mutates a deck and new decks need no migration. That constant lives in `journalExport.ts`, not `App.tsx`, because the export falls back to it too — keeping one definition stops the exported questions drifting from the ones on screen. The consequence is that clearing the box keeps it clear — an empty string is a deliberate choice, not an untouched one — so a reset button restores the prompts, appearing only once the text differs from them.
- **Game notes start blank.** They were once created with `GAME_NOTES_TEMPLATE`, a numbered `1:`–`8:` skeleton matching the General Notes prompts, written into `notes` at creation by `addMatch`, `addGame` and the Replay import. That is gone and the constant with it, so nothing can quietly re-adopt it. Games created before the change keep the skeleton they were stored with — it is the user's text now, not a default to strip. Note the asymmetry with General Notes, which still falls through to `JOURNAL_NOTES_PROMPTS` without storing them; that fallback is in `journalExport.ts` and is unaffected.
- **Match Stats modal** (Journal tab): tiles for winrate, match record, game record and matches logged, plus a per-matchup breakdown (winrate, record, win/loss bar) sorted by matches played. **Winrate counts decided matches only** — draws and matches with no result recorded are excluded from the denominator, since an in-progress match would otherwise read as a loss; a footer states how many were excluded whenever that count is non-zero. Backed by `summarizeJournal` in `journalExport.ts`, sharing `getMatchOutcome` with the text export so "win" cannot drift between the two. Matches with no opponent selected group under "Unspecified". **On the play / on the draw are GAME win rates, not match ones** — play/draw varies between games of a single match, so a per-match figure would be meaningless; the headline Winrate stays per match. Games with no play/draw resolved are excluded from those tallies rather than guessed, and a footer explains the empty tiles when nothing is recorded at all.
- **Journal search (Ctrl+F)**: the Journal intercepts Ctrl/Cmd+F and focuses its own search box (Esc clears and blurs). **Electron's `findInPage` is not an option here**: Chromium's find deliberately skips the contents of form controls, and every note lives in a `<textarea>`, so a native find would match opponent names and headings while silently missing the notes — the one thing worth searching. The search runs over the underlying data instead, matching opponent names and every game's notes, and composes with the archetype filter. Games whose notes matched get a gold left edge (`.game-row-hit`) so a three-game match points at the one that mentioned the card. General Notes is **not** filtered — it is always on screen, so a hit there is reported as a line instead, which otherwise would read as no result at all. Empty results name the active constraints rather than reusing the archetype-only message.
- **Journal archetype filter**: a Matchup dropdown above the match list filters the log to one opponent archetype, each option carrying its match count. Options are built from the matches **actually logged**, not the deck's matchup list, so every option has something behind it and archetypes typed before the opponent field became a dropdown remain reachable; blank opponents bucket under `UNSPECIFIED_OPPONENT`, the same constant the stats modal groups by, so the two cannot categorise differently. A selected archetype stays listed even after its last match is deleted, otherwise the select would show a blank value while still filtering.
- **Filtered journal export**: while a filter is active, a second **Export filtered (N)** button appears beside Clear filter. It passes a deck-shaped copy carrying only the visible matches, so the summary header reports the record against that archetype alone, and passes the archetype as `buildJournalText`'s `filterLabel` so the file carries a `Matchup:` line and cannot be mistaken for a complete log. The plain Export button is untouched — two explicitly-labelled buttons rather than one that silently changes scope. The archetype also reaches the filename, so it goes through `safeFilePart` first (matchup names are free text).
- **Journal export**: an Export button writes a plain-text log via `buildJournalText` — summary header (colors, export time, match count, match and game records), a GENERAL NOTES block (falling back to the prompts when the deck's notes are untouched, so the questions travel with the log either way), then each match with opponent, date and outcome. Each game prints its result and play/draw on **its own line** with the notes flush beneath it and a blank line before the next game; an earlier version put the first note inline and hang-indented the rest, which squeezed long answers into a narrow column. Trailing blank lines are trimmed from the end of the file. Unanswered `N:` prompt lines are exported as-is rather than filtered. A match counts as a Win when game wins exceed losses; a match with nothing recorded reads **Unplayed** rather than counting as a draw, so an in-progress match does not skew the record.
- **Notes fields**: the journal's per-game notes is an `AutoGrowTextarea`, not an `<input>` — an input cannot hold a carriage return at all. `AutoGrowTextarea` caps its visible height at `maxLines` (default 10, 6 for game notes) and then scrolls. It measures `line-height`, which computes to the string `normal` when unset and would yield a NaN height, so any element it styles needs an explicit `line-height` (there is a font-size fallback as a guard). A `ResizeObserver` re-measures on **width** changes — widening the box rewraps the text onto fewer lines while the height measured at the old width stays applied, leaving dead space (very visible when maximising the popped-out Journal). It deliberately ignores height changes: the handler sets `style.height` itself, so reacting to those would loop.
- **Backups**: Electron only — `electronAPI.saveDecksBackup` is called on every deck save; hourly dedup logic lives in the main process.
- **Native dialog focus (Electron quirk)**: after a native `confirm()`/`alert()` closes, Chromium can leave the renderer without keyboard focus — the window looks focused and the mouse works, but nothing typed reaches the page until a focus change jolts it loose. **Never call `confirm()`/`alert()` directly**; use the `confirmAction()` / `alertMessage()` wrappers in `App.tsx`, which call `electronAPI.focusWindow()` afterwards (immediately, then at 50ms and 250ms, since the dialog tears down after `confirm()` returns). The main-process handler does `win.blur()` **then** `win.focus()` — `focus()` alone does not clear the stuck state; the blur is what makes it work, mirroring the click-away-and-back that fixes it manually.
- **Restore backup**: on Electron, `restoreBackup` writes the restored decks straight to storage with `saveDecks` and then calls `electronAPI.reloadWindow()` rather than updating React state. Rebuilding the web contents both loads the restored data and reliably clears the stuck-focus state above. The web build falls back to a normal state update, clearing `selectedDeckId`/`selectedMatchupId` since a wholesale data swap makes any prior selection stale.

## Installer and self-update

The Windows build is an **NSIS installer**, not a portable exe, because only an installed app can update itself: a portable exe has no install location to replace. The two features come as a pair.

### The installer

- **Per-user, one-click** (`oneClick: true`, `perMachine: false`): installs to `%LOCALAPPDATA%\Programs\mtg-sideboard-coach` with no admin prompt, adds Start menu and desktop shortcuts and an Add/Remove Programs entry under HKCU. A per-machine install would ask for elevation on **every update**, which is the opposite of painless.
- **Uninstalling never touches app data** (`deleteAppDataOnUninstall: false`). Verified: deck storage was byte-identical before and after an uninstall, with every backup and MTGA archive intact.
- **Artifact names contain no spaces** (`mtg-sideboard-coach-setup-<version>.exe`). GitHub rewrites spaces in release asset names to dots, which would stop the filename in `latest.yml` matching the uploaded file and break every update.
- **The app is unsigned.** A first install downloaded through a browser gets Windows SmartScreen (*More info → Run anyway*). electron-updater only verifies a publisher signature when a `publisherName` is baked in, which only happens when signing, so unsigned updates install without that check.

### Data continuity: never change `name`

Decks live in `localStorage` inside Electron's `userData` folder, `%APPDATA%\mtg-sideboard-coach`, which Electron derives from **`package.json` `name`** — not from where the app is installed. That is why the dev app, the old portable builds and the installed app all share one data folder, and why the installed app opened with every deck present (checked against the real install). `localStorage` is keyed by the `file://` origin, which every install path shares. **Renaming the package would silently give every user an empty app**; changing `appId` would install a second copy alongside the first. Treat both as fixed.

### How updates work

- **The source is a GitHub Release, never a commit.** electron-builder bakes `app-update.yml` (provider `github`, `Lawgikill/mtg-sideboard-coach`) into the installed app; the updater finds the newest release and reads its `latest.yml`, which names the installer and its sha512. Pushing code reaches nobody until a release is published with the built files attached.
- `updates.cjs` checks **10 seconds after launch** (startup is busy enough without it) and **every 4 hours** (the app is often left open all session). A found update downloads in the background.
- When it is downloaded, a green banner offers **Restart to update**, which calls `quitAndInstall(true, true)` — silent install, then relaunch. Ignoring it is safe: `autoInstallOnAppQuit` installs it on the next normal close, and the banner says so. The home screen shows the version with a manual **Check for updates**.
- **Differential downloads need the previous release's `.blockmap`.** The updater downloads only changed blocks when it can find the installed version's blockmap; without it, it falls back to the full ~125MB download (seen in testing, where the test feed did not host the old blockmap). Always attach the blockmap to a release.
- Dev runs report `unsupported` and never check: there is no installed copy to replace, and electron-updater would throw looking for `app-update.yml`.

### One running copy

`main.cjs` takes `requestSingleInstanceLock()`; a second launch focuses the existing window and exits. Every copy shares one `userData` folder, so two would share one `localStorage` database — the second can fail to open it and start with no decks — and a running copy holds files an update must replace. With shortcuts in two places, launching twice is easy. A consequence for development: **`npm run desktop` exits immediately while the installed app is open**, focusing it instead.

### `ELECTRON_RUN_AS_NODE` in tool shells

Some terminals — VS Code's integrated tooling, and Claude Code's shell — set `ELECTRON_RUN_AS_NODE=1`, which makes **any** Electron exe start as plain Node and exit: the installed app reports `bad option: --enable-logging`, or silently does nothing. `launch.cjs` strips it, which is why `npm run desktop` works. When launching the installed exe from such a shell, remove it first (`Remove-Item Env:ELECTRON_RUN_AS_NODE`). Shortcuts are never affected.

### Testing an update without publishing

`MTG_COACH_UPDATE_FEED` points the updater at any URL serving a `latest.yml` (generic provider) instead of GitHub. The full cycle was proven this way before the first release went public:

1. Build a higher version into a scratch folder without touching `package.json`: `npx electron-builder --win nsis --x64 --publish never -c.extraMetadata.version=1.0.1 "-c.directories.output=<folder>"`.
2. Serve it: `python -m http.server 8731 --bind 127.0.0.1 -d <folder>`.
3. Install the real build (`<installer> /S`), then launch the installed exe with `MTG_COACH_UPDATE_FEED=http://127.0.0.1:8731/` set (and `ELECTRON_RUN_AS_NODE` removed).
4. The server log shows `latest.yml`, the blockmaps and the installer being fetched; the banner appears; Restart relaunches into the new version (Add/Remove Programs and the exe's file version both read it).
5. Clean up: uninstall (`Uninstall MTG Sideboard Coach.exe /S`), delete `%LOCALAPPDATA%\mtg-sideboard-coach-updater` (the downloaded installer is cached there), reinstall the real build.

**Proven on the real path too.** Release 1.1.0 was the first update delivered through GitHub itself: an installed 1.0.0 found it, downloaded it and restarted into 1.1.0 cleanly (confirmed by the owner, 2026-10-22). Both paths are now verified: the generic feed by the local test above, and the GitHub provider by a real release.

This matters because **the updater is the one part that cannot fix itself**: a release with a broken update path can never deliver its own repair — everyone on it would have to reinstall by hand. Test any change to `updates.cjs` or the packaging config this way before releasing.

### Releasing

1. `npm version <x.y.z> --no-git-tag-version`, and add a `CHANGELOG.md` entry.
2. `npm run package:win` — produces the installer, its `.blockmap` and `latest.yml` in `release/`.
3. Commit, tag `v<x.y.z>` (annotated), push `main` and the tag.
4. `gh release create v<x.y.z> release/mtg-sideboard-coach-setup-<x.y.z>.exe release/mtg-sideboard-coach-setup-<x.y.z>.exe.blockmap release/latest.yml --title "MTG Sideboard Coach <x.y.z>" --notes-file <notes>`.

**Never run `npx @electron/asar extract-file … package.json` from the project root.** It writes the packaged, trimmed `package.json` into the current directory, silently replacing the project's own and dropping its scripts, build config and dev dependencies. That happened once while checking the 1.1.0 build and was caught by `git diff` before committing. Use `asar list` to inspect, or extract into a scratch folder.

All three files must come from **the same build**: `latest.yml` carries the installer's sha512, and a mismatch makes every client reject the download. Never publish a draft or prerelease expecting clients to see it — the updater ignores both.

## Removed: the Scout tab

A fourth tab for reading what an opponent boarded in, recorded by hand between games. Deleted once the Replay tab derived the same answer from the log automatically — `MatchupDecklist` is the maindeck panel, `boardedIn` is the diff (with the same unlisted flag and the same "at least N came out" reasoning), and `observedCardsInGame` replaces typing in what was seen.

Two things went with it and have no replacement, deliberately:

- **Live use mid-match.** Scout was usable while the match was still going; the Replay tab reads archived logs, which are swept every 5 minutes and only after MTGA has written them. The answer now arrives after the match rather than between games two and three.
- **"Could still come in"** — their known sideboard cards not yet seen. The decklist block shows the sideboard on file, but does not subtract what has already appeared.

`CardCapture` went with it (its only caller). `useScreenshotOcr` stayed: the Opponent Deck importer still uses it, and it owns the four-copy clamp.

**Four `scout-*` CSS classes survive** — `scout-field`, `scout-ocr-error`, `scout-placeholder`, `scout-select` — because the Replay tab borrowed them. They were deliberately not renamed to `replay-*`: a replay control must never take a class matching an event kind, which is the collision documented under "Searching a replay".

## Replay tab (MTGA log narration, desktop only)

A third workspace tab (after Plans and Journal) that turns MTGA's own logs into a readable play-by-play. Three pickers — **Match**, **Game** (plus "Show All Games"), **Opponent deck** — then the narration, with per-scope copy/download buttons.

### Pipeline

`sweepMtgaLogs` (main process, on ready + every 5 min) copies MTGA's logs into `userData/mtga-logs`, then `mtgaLoadGames` parses every archive, groups games by `matchID`, and attaches a deck.

- **Prerequisite: MTGA's "Detailed Logs (Plugin Support)" setting must be on** (account settings in MTGA; confirmed by the owner). Without it MTGA never writes the `greToClientEvent` game stream to `Player.log`, so archiving still works but every archive parses to zero games. The app does not detect this. "No games found" is the only symptom, which is indistinguishable from not having played.

- **Archiving** copies both `Player.log` and `Player-prev.log` — archiving both buys a one-launch buffer, since MTGA rotates on launch. Archives are named by a **fingerprint of the first 4KB**, not a hash of the whole file: a growing log would hash differently on every sweep and pile up near-duplicates, whereas the head stays stable as MTGA appends, so one archive per session gets refreshed in place. Archiving is unconditional rather than gated on "contains games" — a detection bug would silently lose data. Retention defaults to 7 days.
- **Card names** come from MTGA's own SQLite database (`Raw_CardDatabase_*.mtga`), opened **read-only** since it is MTGA's live data. The join is `Cards c JOIN Localizations_enUS l ON c.TitleId = l.LocId` — the column is `l.Loc`, not `l.enUS`. ~27k names, cached (~60ms). Uses `node:sqlite`, which is experimental but **verified present in Electron 42's bundled Node 24**; being a built-in, it needs no packaging work.
- **Deck attribution** uses **containment of the submitted list within a deck's full 75**, not Jaccard and not against the maindeck alone. A game-two list swaps in sideboard cards, which scored a correctly-matched deck at 0.56 — below any sane threshold; against the whole 75 the same list scores 0.98. Threshold 0.6; below it the match is left unassigned rather than filed under a wrong deck.

### Facts about the log format, confirmed against real data

- Game payloads are **single-line JSON** under `greToClientEvent`. Much of the file is pretty-printed multi-line JSON, which a line-by-line parse must skip.
- The match identifier is **`gameInfo.matchID`** — capital ID. `matchId` finds nothing.
- State arrives as one `GameStateType_Full` per game then hundreds of `Diff`s, so anything needed later must be accumulated as it streams past.
- **Ability ids and card grpIds share one numeric space**, so an ability must never be looked up as a card. `96309` is both the card **District Mascot** and Soul-Guide Lantern's enters-trigger: resolving it as a card made the trigger narrate as `District Mascot resolves` and credited its exile to that card. `nameOf` returns null for anything in `abilityInstances` (objects typed `GameObjectType_Ability`) or `abilityInstanceOwner`; abilities resolve through `sourceOf` instead, which maps the ability *as an ability*. This is also what makes the spells-only filter on `ResolutionStart` actually work.
- **Object ids are renumbered** as cards change zones; `AnnotationType_ObjectIdChanged` must be followed or a card loses its name the moment it is played.
- **Protobuf omits `false`.** `isTapped` vanishes from the message when a land untaps, so presence-in-message is authoritative and an absent boolean means false. Carrying the previous value forward made every land read as permanently tapped.
- **Targets are in the log, but only for your own spells and activated abilities, and not where the name suggests.** `PlayerSelectingTargets` / `PlayerSubmittedTargets` carry the *spell*, not what it targeted (`affectorId` is a bare seat number, details are empty), and no target-shaped field exists on any game object — so those are dead ends. The pick lives in the **`selectTargetsReq` message**, whose `sourceId` matches the cast instance id. A chosen target is the entry offering `SelectAction_Unselect` (once picked, the only thing left to do is take it back); later requests for the same source supersede earlier ones. That request is only sent to the player doing the choosing, so **the opponent's targets can never be recovered** — their spells and abilities correctly get no targeting clause. For an ability, `sourceId` is the ability instance, the same id its `UserActionTaken actionType: 2` names.

### Narration rules

Events are produced during parsing, then rewritten by a chain of passes in `finish()`. **Order matters** — see the regression note below.

- **Opening hands** (`Game start, hand resolution`) are reported when turn 1 is announced, not at game start: a London mulligan draws seven and bottoms back, so earlier than that the hand is not settled. **Mulligans are derived from hand size** (7 − cards held) rather than read from a counter. `mulliganReq` does carry a `mulliganCount` on the second and later requests, but it is sent only to the player being asked, so it can confirm our own count and never the opponent's — the derivation is the only thing that works for both seats. The opponent's hand is hidden by the game, so their line is just the count.
- **The hands thrown away are recoverable, for our own seat.** `recordHandHistory` keeps every distinct hand held during mulligan resolution, which makes the whole sequence readable:
  ```
  Lawgikill's original hand — Bushwhack; Brightglass Gearhulk; 2 Practiced Offense; Forest; Ba Sing Se; and Surrak, Elusive Hunter
  Lawgikill mulligans to 6 — Starting Town; Lavaspur Boots; Practiced Offense; Multiversal Passage; Abandoned Air Temple; Leatherhead, Swamp Stalker; and Bushwhack
  Bottoms Lavaspur Boots
  ```
  - **`mulligans to 6` lists seven cards on purpose.** It names the hand that was *drawn* for that mulligan, before any of it went back, because that is what the decision was made from; the next line says what went back. The kept six is the difference.
  - **Snapshots are taken after the `gameObjects` loop and before `turnInfo`** — that loop supplies the grpIds the names resolve through, and turnInfo is what closes hand resolution. A hand is recorded only when its *contents* change, compared as a multiset so a reorder does not add one.
  - **Partial hands are skipped entirely.** The opponent's ids carry no grpId, so half a resolved hand would be worse than none.
  - The original-hand line needs **three or more** snapshots. With two, the earlier one *is* the hand that was bottomed from, and printing it twice says nothing.
  - **The bottoming transfer is dropped**, since the `Bottoms` line already states it — otherwise it reappears as `puts Lavaspur Boots into their library`, the first line of turn 1. `consumeBottom` is bounded both by the expected count and by `turn <= 1`, so a genuine bottom-of-library effect later in the game is never swallowed.
- **Per-game results are cumulative in the stream — a trap.** Once game 1 ends, its result keeps riding along in every later `gameInfo`, including messages stamped with game 2's number, so assigning by the current game number copied game 1's verdict onto game 2 (a 0-2 match hid this; a 2-1 would not have). A GRE result is only accepted when `gameInfo.stage === 'GameStage_GameOver'`. Games the stream never closes out — a conceded game simply has no GameOver message — are filled from the room's `finalMatchResult.resultList`, which holds one game-scope entry per game **in order**, and are flagged `truncated`. The flag is not displayed — it only drives the concession reading below, since `Conceded — Game lost` already tells the reader the narration stopped short.
- **A cast names where it came from, unless that was the hand** (`casts and resolves Practiced Offense from their graveyard`). The zone is already on the transfer as `zone_src`; `castOrigin` suppresses `hand` as the uninteresting default and drops the possessive for exile, which is a shared zone. Flashback, escape and adventure all change what a play means, and the source zone is the only record that it happened — in a real match exactly 1 of 37 casts qualified, so the line stays quiet unless it matters.
- **A `CastSpell` transfer is not a cast.** MTGA puts the card on the stack while the cast is still being assembled — targets chosen, mana paid — and backing out leaves that transfer in the log with nothing to undo it, so a cancelled attempt narrated as a real cast. In a real match that was 39 transfers against 37 commitments; the two dropped were a Practiced Offense attempt and a Tender Wildguide never actually cast.
  - `findCancelledCasts` walks the log **once before the real parse** and returns the attempts to skip, keyed `<message index>:<instance id>`. It tracks **one open attempt per instance id**: a second `CastSpell` transfer on the same instance cancels the first, which is the only thing that actually marks a cancellation — ids recycle fast, and two different spells plus the real cast all shared id 424 within thirty messages.
  - **An attempt is confirmed by its commitment *or* its resolution**, because MTGA does not always send the commitment. A real Bushwhack — a modal spell prompting `CastingTimeOptionsReq` then `PayCostsReq` — produced no `actionType: 1` at all and no `ResolutionStart` either, just the transfer, its effect and a `ResolutionComplete`. Requiring the commitment deleted a spell that had plainly resolved, taking its whole line out of the narration.
  - **Confirming once is the point.** An earlier version kept a flat list and popped the most recent matching attempt on each signal, so a cast confirmed by its commitment was confirmed *again* by its resolution — quietly reviving the cancelled attempt underneath it and restoring two casts that never happened. One open attempt per instance makes the second signal a no-op. Verified across three archives: the only verdict that changed was Bushwhack.
  - Pre-filtering rather than dropping the events afterwards is deliberate: it keeps a cancelled attempt's `ObjectIdChanged` out of the parse entirely, so no rename ever splices two different cards together.
- **Duplicate copies are not distinguished, deliberately.** An `A`/`B` suffix for same-named permanents was built and removed: instance ids make it easy (`identity` following `ObjectIdChanged`, `battlefieldSeen` recording arrivals), and scoping it to the battlefield kept it to ~5 lines in a match. It still read inconsistently, because only *some* lines about a creature carried the letter and the rest named it bare. If it is ever revisited, every line mentioning a permanent has to be labelled or none of them should be.
- **Activated abilities are narrated** (`LazyPunda activates Riverchurn Monument`). `AnnotationType_UserActionTaken` classifies every player action by `actionType`: **1** casts a spell, **2** activates an ability, **3** plays a land, **4** is a mana ability. Only type 2 is reported — type 4 fires ~80 times a match and would bury everything. The source card comes from `sourceOf` following the ability instance back to its permanent, the same link that attributes tokens and counters. Without this an activated ability showed up only as its consequence: six mill lines with nothing saying who caused them.
- **Sacrificing for mana is narrated, uniquely among mana abilities** (`sacrifices Treasure for mana`). `actionType: 4` is otherwise silent because it fires ~80 times a match for land taps, but one that *eats the permanent paying it* — a Treasure, Clue or Food cashed in — is a real play whose only trace is the sacrifice. Saying what it was for also makes the source redundant, so those lines drop it: a Treasure sacrificed to its own mana ability read `(Treasure)`. Every other sacrifice still names its cause, including when that is the card itself. Detection needs a **look-ahead**: the `UserActionTaken` marking a mana ability arrives *after* the sacrifice that paid for it, so the message's annotations are pre-scanned into `manaAbilities` before any are narrated.
- **A library running dry is reported** (`Lawgikill's library is empty`), which is what explains a game that otherwise just stops on a turn header — the player never got to draw. Emitted only on the transition to zero and only after a positive count has been seen for that zone, because an empty list is indistinguishable from an omitted one. It is also *deferred* until after the message's annotations: zones are read first, so pushing it immediately put the line above the mill that emptied the library.
- **Every finished game closes with `Game won` / `Game lost`.** Appended after every pass so none can fold it in, and only when a result exists. Without it the narration simply stops, which reads identically whether the game ended or the log ran out.
- **A concession is named in the closing line**, two ways. `ResultReason_Concede` on the result is the log stating it outright, and that arrives with the stream intact — it was missed for a while, so such a game simply ended on `Game won` with no explanation. A **missing `GameOver`** is the other, inferred: the result survives only in the match summary. Either way the line reads `Rish concedes — Game won` / `Lawgikill concedes — Game lost`; only the inferred case sets `inferredConcession`, since a stated one is not a guess. Whoever lost the game is the one who conceded, so the name follows from the result. Present tense, like every other line. For the inferred case the reasoning is that the conceding client stops receiving state, so its stream ends before the game does while the match summary still carries the result — and the archive is known not to be truncated, since the room's `MatchCompleted` message appears later in the same file. It remains an **inference** — a disconnect looks identical, MTGA files a concession under the same `ResultReason_Game` as any other finish, and it rests on a single observed match. It was hedged as "likely conceded" at first; the owner chose the plain wording knowingly, so if it ever reads wrong this is the line to revisit, not a bug to rediscover.
- **A concession is not distinguishable.** MTGA reports a conceded game as `ResultReason_Game`, the same value as a normal finish, and no concede-shaped message appears anywhere in the log. The only hint is circumstantial: the narration stops mid-game with the result arriving only in the match summary.
- **How a game or match ended** is reported only when it was not the ordinary way. Each game result carries a `reason` (`ResultReason_Game` is a normal finish) and the room's `finalMatchResult` carries a `matchCompletedReason` (`MatchCompletedReasonType_Success` is normal). `describeEndReason` also suppresses **`Concede`**, which is not an ordinary finish: a win is a win, and the closing line already names who conceded, so `won by concede` in the result read as a qualification on the result itself. Everything else is spaced out and shown — `ended by client disconnect`. **Unknown values are still shown, not suppressed**: a reason worth reporting must not vanish because it was not anticipated.
- **The narration never says "You"** — `seatLabel` always returns the player's name. Both players are named everywhere else, so a second-person label for one of them reads as a different voice. It also only ever appeared on lines built inside `finish()`, since `localSeat` is not resolved until then: a library search left dangling when a game ended rendered as `You searches their library` on a page of `Lawgikill ...`. The old rule — "anything built in `finish()` must read `seatNames` directly" — existed to work around that branch, and is obsolete now the branch is gone.
- **Turn headers are per-player**: `LazyPunda — Turn 3`, not MTGA's global alternating count. `maxTurn` counts a player's own turns too, so the header cannot claim "14 turns" over a game whose last heading reads Turn 7.
- **On the play / on the draw** is exact, not heuristic: whoever takes turn 1 is on the play. Renders nothing when either seat is unknown rather than defaulting.
- **`ResolutionComplete` is not a fallback for a missing `ResolutionStart`.** It was tried, to give that Bushwhack a `resolves` line — the spell did resolve and the log says so, but only through Complete. Two things make it unusable: it lands *after* the spell's effects, so the line reads in the wrong place; and the log can send **two Completes for one resolution** (Practiced Offense did, at msg302 and msg306 of a real game), so any report-once guard keyed on the instance is consumed by the first and fires spuriously on the second. A cast whose resolution was never seen stays a bare `casts X`, which is what that already means everywhere else.
- **Some things the log simply does not record.** That same Bushwhack was paid for with a life-paying land, and the payment block — `ManaPaid`, `ModifiedLife`, the tap — is **entirely absent**, where the Llanowar Elves cast two turns earlier carries all three. There is nothing to recover and nothing to infer from; the narration is silent about it on purpose.
- **`X resolves` is emitted from `ResolutionStart`, not from the `Resolve` transfer.** That transfer is the card *leaving the stack*, which for a sorcery happens **after** its effect — so `Origin of Metalbending resolves` printed below `Glacierwood Siege is destroyed`. A creature's Resolve transfer is Stack → Battlefield, which reads naturally, which is why this stayed hidden. The log's real order is `ResolutionStart` → effects → `ResolutionComplete` → card to graveyard, all in one message. Abilities resolve too and would flood the narration, so this is filtered to spells: `nameOf` resolves card grpIds only and returns null for an ability instance, which is exactly the discriminator needed.
- **`casts X` + `X resolves` collapse** to `casts and resolves X` unless another cast or resolve intervenes, **or a cost was paid in between**. Blocking on *any* intervening event would only have caught 19 of 37 casts in a real match — MTGA emits a spell's effects *before* its Resolve marker, so those events are the spell working, not the stack being contested.
  - **Costs are the exception.** A card reaches the stack *before* its costs are paid (CR 601.2h), so the log genuinely reads cast → pay → resolve. Collapsing across that put `loses 1 life` and `sacrifices Treasure` after `casts and resolves`, implying the spell finished before it was paid for. Events pushed while `castingOpen` carry `duringCast`, and the collapse refuses to cross one. `castingOpen` opens on the `CastSpell` transfer and closes on the `actionType: 1` commitment, with a turn-change reset as a guard. In a real match 33 of 37 casts still collapse; the 4 left split are the ones with additional costs or a contested stack.
- **`relocateTurnEnd` moves two things back a turn.** Both describe a turn that has ended but arrive after the *next* turn's header: cleanup discards (MTGA advances the turn counter before reporting the previous turn's cleanup) and the held-up-mana summary (emitted alongside the new header, but a statement about the player who just finished). Discards are also merged into one line. The cleanup detection is heuristic (beginning phase, before this turn's draw) — the log does not state it.
- **Runs collapse** via the generic `collapseRuns` + `runDescriber(verb)`: mill and draw merge strictly-adjacent runs by the **same player *and* the same source** (`sameActor`). Grouping on the player alone folded two mill triggers resolving back to back into one line, and since their sources disagreed the attribution was dropped entirely — seven cards milled with nothing saying what did it, when it was three from Exhibition Tidecaller and four from Glacierwood Siege. A run is one effect, so the cause is part of what defines it. Grouping is by source **name**, so two copies of a card still merge — and `causeInstance` records which permanent each line came from, letting the credit count them: `(Exhibition Tidecaller ×2)`. That says two triggers fired without having to tell the copies apart, which is the distinction the narration deliberately does not draw. Trailing `×2` rather than a leading `2x` because card lists already use a leading number for quantities (`2 Bejeweled Warg`), and the two must not look alike. 66 mill lines became 9. The count is always the number of **cards**; the list covers only names the game revealed, so an opponent's draws collapse to a bare `draws 6 cards`.
- **Combat collapses by target.** Several creatures attacking one player become `A and B attack LazyPunda`, and their damage becomes `A and B deal 7 damage to LazyPunda (now 8 life)` — summed amount, and the life total taken from the **last** hit in the run, since each blow reports its own running total. Grouped by `targetId` rather than by controller (`collapseRuns` takes a `sameGroup` predicate for this), so a creature hitting a blocker stays on its own line. A run of one is left untouched, which is what keeps the singular verb correct: one creature `attacks`, several `attack`. **Do not sort the attackers to match between the two lines** — the damage order is the order damage was actually dealt, so a first striker appears first there and second in the attack declaration. The apparent inconsistency is real information.
- **Attackers carry their size** (`Keen-Eyed Curator (8/7) attacks Rish`). Every battlefield creature object carries live `power` / `toughness` with counters, equipment, pumps and conditional bonuses already applied, so this is read, never computed (that Curator read 3/3, then 4/3 with Lavaspur Boots, then 8/7 when its exile bonus switched on). The size is the one at the moment the attack is declared, and combat is the only place it is mentioned, because it is where P/T decides things and it adds no extra line. A value only arrives when it changes, so `objectStats` keeps the last one per instance. **An empty `{}` is zero**: protobuf omits a 0, the same trap as `isTapped`, so presence decides and a missing `value` reads as 0 (23 such values in two archives). Merged attacks keep a size per creature, and counting runs on name *and* size, so two identical Elves read `2 Llanowar Elves (1/1)` while a pumped one stays separate. Cross-checked against combat damage: every unblocked attacker's power equalled the damage it dealt, and merged attacks summed correctly.
- **A damage line makes both sides hoverable.** It carried only the source in `cards`, so a creature being hit had no preview,. Damage to a *player* stays a seat label with nothing added.
- **Damage merges with its life loss** — but only when the numbers match exactly (life lost === damage dealt, to that player) **and the source matches** (`ModifiedLife`'s affector is the creature that dealt the damage). Life changes constantly for other reasons (shocklands, pain lands, lifegain); adjacency alone would invent causes. Creature damage correctly keeps no parenthetical.
  - **The life line is not always adjacent.** A combat damage step is one message that reports every blow first and every result after: `Pawpatch Recruit → Jace`, `Leatherhead → Rish`, `Jace loses 2 loyalty`, `Rish loses 6 life`. Requiring adjacency left that Leatherhead hit split in two (a double-striking Pawpatch shared the regular damage step with it). `mergeDamageLife` therefore searches forward past the step's other `damage` / `counter` / `life` lines and stops at anything else. Each life line is claimed once, in order, so two copies of a card hitting the same player each take their own — the adjacent-only version would have given the merged run the *first* hit's total and stranded the second life line.
- **Lists use semicolons, not commas**, because card names contain commas (`Leatherhead, Swamp Stalker`). Duplicates become counts (`2 Bejeweled Warg`) via `countedList`, keeping first-appearance order.
- **Holes that were closed** (the log reported these; the narration said nothing): `SBA_Damage` — a creature dying in **combat** does not go through `Destroy`; `SBA_UnattachedAura`; `SBA_ZeroLoyalty`; `Surveil`; `Countered`; and `Put` — a look-at-the-top effect reporting what it took and what it bottomed.
  - **Every unhandled `category` on a `ZoneTransfer` is a silent drop**, so the set is worth re-checking against real logs rather than extending one bug report at a time. Counted across three archives: `Draw` 78, `CastSpell` 72, `Resolve` 67, `Mill` 66, `PlayLand` 48, `Put` 18, `Exile` 11, `Destroy` 8, `Sacrifice` 7, `Discard` 6, `SBA_Damage` 5, `Return` 4, then **one each** of `SBA_ZeroLoyalty`, `Surveil`, `Countered`, `SBA_UnattachedAura`, `nil`. The long tail is where the holes live, and a category appearing once in three archives still swallowed a planeswalker dying.
  - **`SBA_ZeroLoyalty`** is a planeswalker leaving on zero loyalty — a state-based action, not a `Destroy`, so like `SBA_Damage` it fell through. Its loyalty counters ticked away to nothing and the walker simply stopped being mentioned. Worded `is put into the graveyard with no loyalty left` rather than "dies", which is a creature's word.
  - **`Countered`** is the one case where the log names the cause outright. The `nil` branch below it only knows that a spell left the stack without resolving and deliberately will not guess why; `Countered` does not have to. The transfer's affector is the countering spell itself, so the line credits it like any destroy or exile: `Leatherhead, Swamp Stalker is countered (Three Steps Ahead)`. That is read from the log, never inferred from whatever was cast just before.
  - **The opponent's Spree modes are not in the log.** Three Steps Ahead left no `ChoiceResult` and no mode field on its game object, and the casting-time choice goes only to the caster — *your own* are, through the casting-time replies above. In the observed case the effect itself (the `Countered` transfer, and nothing else in the resolution) together with the mana paid (exactly 3 = {U} + the counter mode's {1}{U}) settled it. That is card-specific arithmetic repeating what the next line already says, so nothing narrates it. `selectDescriber` merges a run into one sentence (`puts a card into hand and a card on the bottom of their library`), saying the destination once when every card went the same way (`puts Seam Rip and Meltstrider's Resolve into hand`). Face-down cards collapse to a count via `cardLabels` — `puts 2 cards into hand`, never `2 a card`.
- **A spell that never resolves is reported** (`Into the Flood Maw never resolves`). The signal is a transfer off the stack whose category is the literal string `"nil"`, with no `ResolutionStart` — the same card cast successfully later produces `ResolutionStart` → effects → `ResolutionComplete` → `Resolve`, which is what makes the distinction certain rather than inferred. The kind is **`unresolved`, not `fizzle`**: a fizzle is specifically a spell countered by the rules for losing its last legal target, while a counterspell is a different mechanism with the same outcome, and the log cannot tell them apart. The branch and the wording name the shared outcome, never a cause.
- **Life changes name their cause** where the log allows: `loses 1 life to Starting Town`, `gains 3 life from Vigorbloom Charm`. A painland's life loss comes from an **ability instance that never arrives as a game object** — the link exists only in `AnnotationType_AbilityInstanceCreated` (ability id → the permanent that made it), so `objectSourceGrpId` cannot see it. Those ids are reused through the game, so each creation overwrites the last. A **shockland's** affector is a synthetic engine id that is never defined anywhere, so those stay unattributed rather than being pinned on whatever happened nearby.
- **Restriction sentences are dropped from activation lines** (`Ba Sing Se: Earthbend 2, targeting Plains`, not `…Earthbend 2. Activate only as a sorcery, targeting Plains`). A sentence like "Activate only as a sorcery" or "…only once each turn" describes legality, not what happened, and an activation that appears in the log has by definition already satisfied it, so it can never say anything in a replay. MTGA templates all ~620 of them as a sentence starting `Activate only`, which is the whole rule in `dropRestrictions`. It was checked against **all 21,664 entries** of MTGA's ability table, comparing old and new output: 635 changed, none emptied, no quote left unbalanced. Three things that check caught:
  - **Whitespace must be preserved.** The first version split on whitespace and rejoined with spaces, which collapsed the line breaks between modal bullets (`Choose one — •A •B`) in ~550 abilities that have no restriction at all. Separators are now captured by the split and put back.
  - **A restriction can follow a closing quote** (`…can't be blocked." Activate only as a sorcery`), so sentences split after `.` *or* `."`.
  - **A restriction inside a quoted, granted ability is kept**, since cutting it would describe the wrong ability. Conversely, granted abilities are stored with the parent card's closing `"` / `]` / `)` stuck to their last sentence, and dropping that restriction removes the stray mark too, leaving the line cleaner than before.
- **Activated abilities carry their targets too** (`activates Lavaspur Boots: Equip {1}, targeting Plains`). The timing is the reverse of a spell's: a spell's cast line exists before its targets are chosen, so they are patched onto it, but an ability's targets are chosen *first* and its line is only written on the commitment that follows. `recordTargets` therefore holds unmatched targets in `abilityTargets`, keyed by the ability instance and **already resolved to names**, and the activation consumes them when it is written. The map is cleared every turn, so a stale entry can never be picked up by a later ability that happens to reuse the id. It earns its place on the turns where the effect never happens: an equip onto an earthbent Plains that was killed in response left no `attaches` line at all, and the target was the only record of what had been attempted. Where the ability does resolve, the next line usually restates the target, the same redundancy spells already accept.
- **Targeting is resolved at capture time, never later.** `recordTargets` turns target instance ids into names the moment the request arrives and patches them onto the cast event already pushed. Resolving in `finish()` instead attributed Meltstrider's Resolve to whatever had inherited id 334 by the end of the game, and keying a map by instance id let Tender Wildguide inherit Practiced Offense's targets — both genuinely used id 424 in one game. Ids are renumbered *and* reused within a game; only the live mapping is trustworthy.
- **`AttachmentCreated` narrates auras and equipment** (`Meltstrider's Resolve attaches to Brightglass Gearhulk`). It matters because it is *game state*, not a private request: unlike `selectTargetsReq` it crosses the visibility line, making it the only record of what an **opponent's** aura was put on. It pairs with the `SBA_UnattachedAura` transfer that reports the aura falling off later. `mergeResolveAttach` folds it into a standalone resolve (`Meltstrider's Resolve resolves and attaches to Brightglass Gearhulk`) — but only a standalone one: where the cast and resolve already collapsed, the attach stays its own line rather than being bolted onto a sentence that may already carry a targeting clause naming the same permanent.
- **An attribution is hoverable like any other card name.** Every event carrying a `source` gets it folded into `cards` by a single pass at the end of `finish()`, rather than at each narration site. A source can be set where the line is written, carried through a run collapse, or introduced by a merge, and each of those would otherwise have to remember — 44 events in a real match.
- **Any merge that rebuilds a sentence must re-place the trailing credit, and strip the one the absorbed line carried.** This has bitten three times: `selectDescriber` silently dropped the cause, `mergeScryDraw` left `(Opt)` mid-sentence, and once draws gained their own cause it printed `(Opt) (Opt)`. A credit is a field on the event, never something to leave sitting in the text being folded in.
- **`mergeScryDraw` folds a scry into the draw that follows it** (`puts 1 card on the bottom (Opt) and draws a card`) — one spell doing its job. Only when the draw is the very next thing the same player does, so an unrelated draw later in the turn stays separate. It runs *after* the draw collapse so a multi-card draw merges as one clause rather than the merge swallowing only the first of six.
- **Your casting-time choices are recorded: modes and optional costs** (`casts and resolves Pawpatch Recruit with offspring`, `casts Bushwhack, choosing "Search your library for a basic land card…"`). MTGA asks with a `castingTimeOptionsReq`, and the client answers with a `castingTimeOptionsResp`: `CastingTimeOptionType_Modal` carries `chooseModalResp.grpIds` (the chosen modes' ability ids, resolved through the ability text table and shown whole, in quotes), and `CastingTimeOptionType_AdditionalCost` names the option by `ctoId`, whose ability text gives the keyword (`Offspring {o2}` → `with offspring`; the same reading covers kicker, bargain, gift).
  - **The reply is a multi-line client-to-GRE block**, so `findCastingChoices` reads it from the whole text, sharing the single read with `findSideboarding`. It returns one entry per request **in file order**, each carrying the request's own `msgId` / `gameStateId`; the main parse checks both before using an entry, so a misalignment can only drop a choice, never attach one to the wrong spell. Ids are taken with a greedy prefix (`/[^]*"msgId":…/`), because a line can pack several messages and the first id in the look-back may be an earlier one's.
  - **The cast must be the same instance *and* the same card**, in the current turn. A reply to an attempt that was then cancelled (one Vigorbloom Charm, in a real game) has no cast line of its own and must not land on whatever reused the id. Trigger modes (Bejeweled Warg's) are replies too but have no cast line, so they attach to nothing.
  - Order on the line is cost, then mode, then targets, since the mode says what the targets are for. Only your own choices are ever sent to you. Only an accepted additional cost has been observed; what a declined one looks like is unverified, and anything that is not an `AdditionalCost` or `Modal` reply is ignored.
  - Verified by diffing the full narration of all four games against the previous commit: exactly the five affected cast lines changed.
- **Modal choices are recorded.** `AnnotationType_ChoiceResult` gives `Choice_Value` as a **localization id** (`Choice_Domain: "localization_id"`), resolved against `Localizations_enUS` — the same table the card names come from — so `casts and resolves Glacierwood Siege` is followed by `chooses Temur for Glacierwood Siege`. `loadChoiceLabels` caches only strings of ≤120 chars: a mode label is a few words, while that table also holds every card's full rules text, so the cap halves the map (~5MB vs ~9MB) at no cost in coverage. A non-`localization_id` domain renders nothing rather than a raw number. `mergeChoiceIntoCast` then folds the mode onto the line that cast it (`casts and resolves Glacierwood Siege, choosing Temur`); it searches backwards up to 8 events rather than requiring adjacency, because the choice is logged on resolution and the spell's own effects can be reported in between, but never past a turn boundary. A card choosing twice reads as one clause (`choosing A and B`).
- **Named cards and chosen types are recorded too** (`Rish plays Petrified Hamlet, choosing Fountainport`; `Lawgikill plays Multiversal Passage tapped, choosing Forest`). Both are `ChoiceResult`s, and both are **public** — MTGA shows the choice on the permanent to both players, so the opponent's arrive like your own, unlike targets. They were silently dropped because the handler accepted only the `localization_id` domain. The domain decides which table resolves the value, and anything unrecognised stays silent rather than printing a raw number:
  - **`13` is a card name**, the value being the name's localization id (811887 → "Fountainport"), resolved through the same labels as modes. The permanent also carries a persistent `LinkInfo` with `ChooseLinkType: "CardName"`. A named card joins `cards`, so it previews.
  - **`9` is a subtype** from MTGA's `SubType` enum (29 → Forest), via `loadSubTypes`; its `LinkInfo` says `ChooseLinkType: "Type"`. A type is not a card, so it is not linked. `loadSubTypes` and `loadCounterTypes` now share one cached `loadEnumLabels(type)`.
  - Each domain was seen **once**, so its reading rests on a single example, cross-checked against what the card asks for ("choose a land card name", "choose a basic land type").
  - **A land's choice folds onto its play line**, and `mergeChoiceIntoCast` accepts `play` hosts. A choice made *as* a permanent enters ("As this land enters, choose…") is logged **before** the transfer that plays it, so a standalone choice is held for up to 3 events and folded into the next play or cast of the same card by the same player. That window is short, and the match strict, so it cannot reach an unrelated later copy. Diffed against the previous commit: exactly these two lines changed.
- **`mergeSharedSource` joins adjacent lines crediting the same source**, stating the credit once: `Leatherhead, Swamp Stalker loses a +1/+1 counter and Glacierwood Siege B is destroyed (Leatherhead, Swamp Stalker)` — a cost paid and the thing it paid for, read as one sentence. Covers `counter`, `destroy`, `exile`, `return`, `token`, `sacrifice` and `draw` — the last two give `sacrifices Soul-Guide Lantern and draws Starting Town (Soul-Guide Lantern)`. `sharedOpening` drops words the two clauses begin with in common, so one player acting twice is not named twice, and `sacrifices X and sacrifices Y` folds to `sacrifices X and Y`. Whole words only and never the whole clause: `draws Forest` beside `draws Forest Tentacle` shares `draws `, not `draws Forest`. **And never cutting into a card name** — whole-word safety is not enough on its own, because a card name is several words. Two legendaries sharing a first word did it: `Chandra, Torch of Defiance gets a Loyalty counter` beside `Chandra, Chill of Compliance is exiled` dropped the shared `Chandra,` and left "Chill of Compliance", a card that does not exist. `sharedOpening` takes the merged line's card names and refuses any opening that would split one; only a clause *beginning* with a card name can be split that way, so `draws Forest` is untouched. **Adjacency and a shared source together** are what make it safe; either alone would fold unrelated events together. The cause is carried as a `source` field (not parsed back out of the text), which is why `causeOf` returns the name rather than a formatted fragment. When both lines share a **predicate** — two cards doing the same thing — it is said once and the verb goes plural (`Bejeweled Warg and Brightglass Gearhulk return to hand (Aetherize)`), which is why `destroy`/`exile`/`return` carry a `subject` and a `predicate: { one, many }`. Differing predicates fall back to joining the two sentences, and a merged sentence drops its predicate so a third line cannot factor against half of it.
- **Token lines always say "token", and a copy says so with its size** (`creates a Map token`; `creates a 1/1 token copy of Pawpatch Recruit (Pawpatch Recruit)`). The log is explicit on all three counts: the annotation is `AnnotationType_TokenCreated`, the object is `GameObjectType_Token`, and a copy carries `isCopy: true` with its own power/toughness — an offspring copy is 1/1 where the card is 2/1, so "token copy" alone would misstate it. Without the word, a token named after a real card read as the card. `isCopy` is presence-authoritative like `isTapped` (protobuf drops a false), tracked in `objectCopies`. Counted copies keep the size after the name (`2 token copies of X, each 1/1`) so two numbers never sit side by side.
- **A token's hover shows the token, not the card it is named after.** Tokens are also indexed under `tokenKey(name)` and `tokenKey(name, power, toughness)` (`token:pawpatch recruit:1/1`) in `createCardIndexes`, since the plain name rightly belongs to the real card. Each token line carries `tokenRefs` (name + size from the log, carried through merges), and `tokenPreviewAt` — shared by the screen and the HTML export — treats only the occurrence directly after `token copy of` or directly before ` token(s)` as the token: the `(Pawpatch Recruit)` credit on the same line stays the card. The sized key matters beyond copies: same-named tokens come in several sizes (Soldier 1/1, 1/2, 2/2), and a name-only lookup showed whichever was indexed first. Proven against Scryfall's real objects run through the real index: the copy resolved to the 1/1 token (tblb #21), its credit to the 2/1 card (blb #187), and a 1/1 Soldier resolved correctly with a 2/2 Soldier deliberately indexed ahead of it. A token the database lacks falls back to the plain name.
- **Identical tokens from one source collapse to a count** (`Lawgikill creates 2 Map tokens (Get Lost)`), via `tokenDescriber`, grouped on player, source *and* token name so different tokens never fold together. Without it Get Lost and Elspeth's doubled Soldiers read `creates a Map and Lawgikill creates a Map`. The count goes before `<name> tokens` rather than pluralising the name, which would break on irregular plurals (Wolf, Elf). Single token lines take "a"/"an" by first letter (`creates an Illusion token`). Grouping also requires the same copy flag and size.
- **A merged sentence folds against its *last* clause.** `mergeSharedSource` keeps `lastClause`, so a third line compares its opening with the clause directly before it, not with the sentence's start: `Brightglass Gearhulk is destroyed and Lawgikill sacrifices Soul-Guide Lantern and draws Forest`. Comparing against the whole sentence never matched once the first clause was about something else, and the player was named again.
- **An unresolvable affector is an ability id, not a card.** When an effect's affector appears in no game object and is not a card grpId, it is an entry in the `Abilities` table — and `Cards.AbilityIds` (`"6:158,14:28,176578:879294"`) maps it back to its owner. `loadAbilityOwners` inverts that into ~16k mappings (79ms, cached) and `sourceOf` uses it as a last resort, which is how `176578` resolves to Brightglass Gearhulk. **Only abilities owned by a single card name are kept**: the low ids are evergreen keywords shared by thousands of cards, and mapping those would attribute a trigger to whichever card happened to be listed first.
- **Library searches are narrated, including fruitless ones** (`searches their library and takes 0 of 1 option (Brightglass Gearhulk)`). `searchReq` names every legal candidate (`itemsSought`), the limit (`maxFind`) and the source, but **not what was taken** — that only emerges from the `Put` transfers that follow, so `concludeSearch` holds the line open, counts library→hand puts, and closes on the `Shuffle` that ends a search. The cards taken are **absorbed into the line** (`takes 2 of 9 options: Seam Rip and Meltstrider's Resolve`) rather than repeated on their own line below it, with a colon introducing the list as milling and discarding do. The line is then **spliced in at the index where the search opened**; everything absorbed sits after that index, so removing it first leaves the index valid. Selections with no search behind them — Sleight of Hand, Stock Up, Flow State — keep their own lines untouched. A search that takes nothing is otherwise completely invisible: the permanent resolves and the narration moves on. Like `selectTargetsReq`, this is a request to the searching player, so the opponent's searches cannot be seen.
- **Card selection names its cause too** (`puts Seam Rip and Meltstrider's Resolve into hand (Brightglass Gearhulk)`). `selectDescriber` rebuilds its text from scratch, so a cause shared by the whole run has to be re-applied there rather than inherited — a merged line would otherwise silently drop it.
- **A departure names its zone when it was not the battlefield** (`Glacierwood Siege A is exiled from LazyPunda's graveyard`). "Is exiled" otherwise reads as coming off the board, which is wrong for graveyard hate; the battlefield is the default and says nothing, mirroring `castOrigin`. The owning player is named because a card can be exiled from either graveyard. `departureZone` applies to `Exile` and `Return`, and the zone must also go into the `predicate` — otherwise two merged exiles would factor to a shared clause stating only one of their zones.
- **Battlefield departures name their cause** (`Glacierwood Siege B is destroyed (Leatherhead, Swamp Stalker)`, `Bejeweled Warg returns to hand (Aetherize)`). `Destroy`, `Exile` and `Return` are otherwise passive sentences with no agent, which is what made a triggered ability's destroy look unrelated to the cost paid two lines above it. The annotation's affector is an *ability instance*, so `credit()` follows the same link that attributes tokens and counters, and suppresses the cause when it is the card itself. A triggered ability's whole chain is in the log — the trigger's `AbilityInstanceCreated` names the permanent that made it, and the resulting transfer's affector is that ability.
- **Tokens and counters are attributed through the ability.** An annotation's affector is usually an *ability instance*, not a card, so `sourceOf` follows `objectSourceGrpId` back to the card — that is what turns "creates a Treasure" into `creates a Treasure (Bejeweled Warg)`. A counter **always names its source, including when that is the card itself**. It reads redundantly in isolation (`Leatherhead gets a Hexproof counter (Leatherhead, Swamp Stalker)`), but a counter a permanent puts on or takes off itself is the cost or effect of its own ability, and naming it is what ties the line to the other lines of the same trigger — a counter removed as a cost otherwise looks unrelated to the destroy it paid for. This was suppressed twice before and reinstated both times for that reason; the source is also what runs group by, so dropping it stopped the two halves of one effect from merging at all. **Counter kind comes from MTGA's `Enums` table**, not from inference: `SELECT Value, LocId FROM Enums WHERE Type = 'CounterType'` joined to `Localizations_enUS` gives all 220 kinds (`1` → `+1/+1`, `138` → `Hexproof`). Some values repeat with display markup (`<nobr>+1/+1</nobr>`), so `loadCounterTypes` keeps the first clean label per value. An earlier version inferred +1/+1 from a `PowerToughnessModCreated` in the same message, which was honest but could only ever name that one kind — the enum names every counter in the game, so the correlation code was removed. Counters from one source onto several creatures merge via `counterDescriber` (`A and B get a +1/+1 counter (Practiced Offense)`), grouped on source + kind + amount + direction so an unrelated counter never folds in; `counterPhrase` builds both the single and merged forms so they cannot drift.
- **A permanent becoming a creature is reported** (`Plains becomes a creature`, after an earthbend). No annotation states it: the object is re-sent with `CardType_Creature` in its card types, so `noticeAnimation` compares each object with its last report in `objectShape`. Without it, a land took +1/+1 counters, was equipped, damaged and died with nothing saying why that was possible. Deliberate limits:
  - **Only gaining Creature.** Vehicles and most animated lands revert at end of turn, so "stops being a creature" would be a predictable line every turn.
  - **Only a permanent already on the battlefield.** One entering as a creature is not becoming one, and a zone change gives it a new id with no history, so the earthbent Plains returning from the graveyard produces no second line.
  - **No size.** The counters that animate it often arrive in the same message, so the first size seen already includes them: `becomes a 2/2 creature` followed by `gets 2 +1/+1 counters` would read as 4/4.
  - **No cause.** No annotation names what animated it, and the line sits directly under the ability that did.
  - Checked across every archive by diffing the full narration against the previous commit: exactly one line added, the earthbend's.
- **A land entering tapped says so** (`plays Temple Garden tapped`). Read straight off the object's `isTapped` in the message the land arrives, which the gameObjects loop has already applied by the time annotations are handled. It distinguishes a shockland paid for from one that cost a turn — 4 of 25 land plays in a real match, so the line stays quiet otherwise.
- **Each turn closes with what the player is left holding** (`LazyPunda ends with 32 cards in library, 7 in hand`). **Only the player whose turn it was** — both players' counts on every turn would double the lines to say half as much per line, and the number that matters is the one belonging to whoever was acting.
  - **Hidden zones still ship their size.** `ZoneType_Library` is `Visibility_Hidden` and `ZoneType_Hand` is `Visibility_Private`, but both carry one placeholder instance id per card, so the array length is the count even where the identities are not ours to see. That is what makes the **opponent's** hand size knowable — the same fact the mulligan derivation already rests on.
  - **Counts carry forward.** A diff only names zones that changed, so the opponent's library goes unmentioned for several turns at a time; `handSizes` / `librarySizes` hold the last known value per seat and reset per game.
  - Unlike `handZones` beside it, an **absent id list reads as empty rather than as unchanged**: a zone named in a diff is being reported, and protobuf omits the list when there is nothing in it. Treating absence as "no change" would freeze a hand at its last non-zero size.
  - Skipped on turn 1, which closes no previous turn. The **last turn of a game gets no line**, since nothing follows to trigger it — the same limitation the mana line has.
- **Held-up mana**: a closing line on each turn stating that player's untapped lands (`has 4 of 5 lands untapped` / `is tapped out`), i.e. what they carry into the opponent's turn. This is the only useful product of 159 tap events — individually noise, but the count at that moment is what they are representing. It is *emitted* when the next turn starts and relocated by `relocateTurnEnd`, because that is the first moment the state is final.
- **The sticky game heading pays for its own spacing with padding, not margin.** A margin is not painted with the background, so a 26px `margin-top` left a transparent band through which scrolling narration stayed visible above the frozen heading. `.replay-log` also carries no top padding for the same reason — a sticky element parks at the scrollport top, *above* the container's padding, so that padding is another see-through gap. Space at the very top comes from `.replay-log > :first-child` instead.
- **No minor/suppressed events.** The "Show minor events" toggle was removed: mill is real information and always shows, and `is unblocked` is dropped at the source since the damage line that follows says the same thing.
- **Pass order matters.** The turn-closing summaries are emitted *with the next turn's header*, because that is the first moment the turn's state is final — so they land between the header and the cleanup discards. An earlier version of the relocation scanned for discards immediately after the header and silently stopped working the moment the mana line was added; every cleanup discard stranded itself under the wrong turn again. `relocateTurnEnd` collects the whole block before deciding where it goes, and the kinds that belong to it are named in **`TURN_END_KINDS`** (`counts`, `mana`) rather than tested one at a time. Anything new emitted at a turn boundary goes in that set, or it strands itself under the following turn. Within the turn the discard comes first — it is an action *in* the turn, while the summaries are what it closes on.

### Searching a replay

**Ctrl/Cmd+F focuses the tab's own Find box**; Esc clears and blurs, Enter steps to the next hit and Shift+Enter to the previous, with ↑/↓ buttons and an `n of m` counter beside it. Hits get a gold left edge, matching the Journal's search; the current hit is also filled so stepping is visible.

Unlike the Journal, Chromium's `findInPage` *would* work here — the narration is ordinary DOM, not textareas. It is still not used: Electron ships no find bar, so one would have to be built regardless, and findInPage only highlights. A replay runs to pages, so **stepping between hits is the point**, which means owning the match list.

**Never give a replay control a `replay-<name>` class matching an event kind.** Each narration line is classed `replay-${event.kind}`, so the Find box named `.replay-search` applied its `max-width: 260px` to every *library search* line — which wrapped mid-sentence in a window with room to spare, looking like stray line breaks in the data rather than a style. The control classes are `replay-find*`.

Hit numbering is **one flat sequence across every rendered game**, computed before render, so "Show All Games" steps across a game boundary without special handling. Element refs live in a `useRef` map rather than state: they are written during render and reading them must not cause another.

### Game summary

`OpponentSummary` renders the **match** block, between the header and the first game (only when more than one game is shown). Per game, the only summary block left is the boarding inference — see "There is no per-game list" below. The Summary toggle controls both.

Both headline counts are **copies, not distinct names**: a list showing `3 Breeding Pool` has shown three cards. The two numbers on screen therefore mean one thing. (This is separate from how the per-card counts themselves are derived, below.)

**The match counts are the highest seen in any one game, never a sum** — two Opts in game 1 and two in game 2 is evidence of two copies, not four. `observedOpponentCards` takes that maximum per card; verified against the per-game figures with zero disagreements.

**The toggle governs the exports too.** `buildReplaySummaries` prepares both scopes once in `ReplayView` — undefined while the toggle is off, which is the whole of how it stays out of a file — and that one object feeds the on-screen blocks, the decklist's seen-marking and both export formats. Preparing it at each of those sites instead would let a file list different cards, in a different order, from the screen it was taken from. `OpponentSummary` renders a prepared `ReplaySummary` rather than computing one, and `cards` stays as `[name, count]` pairs because the screen attaches a hover preview to each card, which a formatted string could not carry.

**The match-wide block only goes on a file that covers the whole match.** Across two games it is a different claim from either game's own list; on a single-game export it would merely repeat the block directly below it. That mirrors the screen rule exactly (`!game && match.games.length > 1`).

In text the block sits under the header for the match and under the `GAME N` rule for a game, **one card per line**. This is the one list that does not use the narration's semicolon convention: that convention exists for lists inside a sentence, and a sixteen-card run wrapped across three lines of prose cannot be scanned for a card. `summaryLines` deliberately appends **no** trailing blank line — both callers already follow it with one, and adding a second put two blank lines between the summary and the first game. In HTML it is a `.summary` panel whose names keep working hover previews, through the same `renderText` the narration uses.

**There is no per-game list of what they showed.** It was built and removed: every card in it already appears in the match block above, and in a game after the first the part that actually differs is exactly what the boarding block states. Game one's was kept briefly as "the baseline the diff works from" and dropped too — the match list plus the boarding deltas carry it. A per-game `ReplaySummary` now holds only `boarded`, which is why every renderer treats an empty `cards` as "skip that row" rather than "render nothing".

A **Summary** toggle in the replay bar puts a block at the top of the match listing every card the opponent was seen to own — at the top because "what did they have" is the question a replay is opened with, not something to scroll to. Names are hoverable like any other.

`observedCardsInGame` is shared with the archetype guesser, so the two can never disagree about what counts as seen. Two things it gets right that are easy to get wrong:

- **Presence and copies are counted separately.** Any ownership event puts a card on the list; a copy is counted only when the card **leaves a hidden zone** — `event.fromZone` of `hand` or `library`. Counting every event made one creature that was cast, attacked, was exiled and died read as **4 Exhibition Tidecaller** when two were ever on the battlefield. Counting entries into play fixed that but missed **discards**, which never enter play yet are plainly copies. The hidden-zone rule covers both, and correctly ignores a spell recast from the graveyard — a copy already counted.
- **`fromZone` must survive the merges.** The merged cleanup-discard, `runDescriber` and `selectDescriber` all rebuild events, and without carrying it through, every card an opponent discarded was invisible to the summary.
- **`mergeSharedSource` destroys more than that, so it records `origins`.** It sets `card` to null, keeps a single `fromZone`, and takes the **first** line's `kind` — so a Chandra exiled from its owner's library, merged into the counter that exiled it, stopped looking like an ownership event at all and was skipped whole. The summary then reported one copy of a card seen twice. Each folded-in line now contributes `{ card, seat, fromZone, kind }`, and the summary reads those per contribution rather than reading the merged line. **Seat and kind are both per entry**: these lines pair on a shared *source*, not a shared player, and an exile folded into a counter is still an exile. Diffed against the previous logic across four real games, exactly one count changed — the one that was wrong.
- **`cards` is read only for `discard`, `mill` and `select`**, whose lists belong to the event's own seat. A merged line drops its single `card`, so those kinds would otherwise contribute nothing. Every other kind reads `card` alone, since a merged line there names cards acted *on* rather than owned. The `source` is always excluded — it is appended to `cards` to keep attributions hoverable and can belong to either player.

### What *we* boarded in — exact, from our own submission

The log states our own sideboarding outright, so it is never inferred. Before each game after the first the GRE sends `GREMessageType_SubmitDeckReq` carrying the deck as it stood, and the client answers `ClientMessageType_SubmitDeckResp` with the list actually submitted; diffing the two `deckCards` multisets gives in and out exactly. Verified against a real match: 10 in, 10 out, 60 → 60 and 15 → 15.

**Only ours.** The opponent's submission is sent to the opponent, which is why their side has to be guessed from what they were seen to play.

**The response is a pretty-printed multi-line block**, because it travels client-to-GRE rather than in the single-line `greToClientEvent` stream — `parseLogFile`'s line-by-line loop cannot see it at all, and silently skips it as unparseable. `findSideboarding` therefore reads the file as one string and brace-matches, unlike `findCancelledCasts` which streams. These blocks are a handful per log, so the cost is nothing and it is the only thing that works.

**A step belongs to the game after the last one named.** Boarding happens between games, so the submission sits between the last `gameNumber: 1` marker and the first `gameNumber: 2` — confirmed by offset against a real log. The match comes from the last `matchID` before it, and a response is paired with the nearest preceding request, since the client cannot be asked for a second list without having answered the first.

Note the parser *already* captured `submitDeckReq` into `submittedDecks` for deck attribution; what was missing was only the response.

It has **its own toggle**, separate from Summary: one is about them and inferred, the other is about us and exact, and they are wanted at different times. Rendered green against the opponent block's amber, and stated with no hedging.

### What they boarded in

Every game after the first carries a second block under its summary — never under the match summary, since boarding is a per-game act: `Possibly boarded in — 4 cards:` followed by the list. The count is **copies, not distinct names** (two Negate is two cards in, and two cards out), matching the match summary's headline count, which counts the same way. It is stated as what the evidence *allows*, never as fact, because a card can go unseen in game one and still have been maindeck.

**Two baselines, chosen by whether the saved list is complete.** `boardedIn` counts the matchup's sideboard on file; **exactly 15** makes it a complete template, and anything else makes it a partial record.

- **Complete** — baseline is their maindeck on file *plus* whatever game one revealed. A card seen beyond that must have come from somewhere, and the sideboard is the only candidate.
- **Partial** — baseline is game one alone. A partial list's absences mean nothing, so reading them as sideboarding would invent it out of missing data.

In both, game one is the floor: a card seen before boarding is maindeck by definition. Quantities take the **higher** of maindeck-vs-seen rather than the sum, so a list running 4 Forest against 2 seen still accounts for only 4.

**Game three is measured against game one, never game two.** A card seen in game two was itself boarded in, so using it as a baseline would hide exactly what is being looked for.

**Lands are excluded entirely.** A fifth Plains in game two says the deck drew lands, not that it boarded them, and a manabase is the part of a list a partial record is least likely to hold — lands were the loudest source of false positives. Decks that genuinely board lands exist; this trades those rare cases for a signal that is readable the rest of the time. Judged on the **front face**, as type grouping is everywhere else, so a modal card with a land back still counts as a spell. A card the database does not know is kept rather than guessed at.

**The basis is a tooltip** (`measured against their 75 on file` / `measured against game 1 only`). Which baseline was used says how much weight the inference carries, so it is never dropped — but it is not what the line is read for. It rides on `title`, which needs no script and so works in the static HTML file too. A **text export has no hover**, so there it prints as a trailing line; that difference is the format's, not the data's.

**An unlisted card gets an asterisk** — absent from both the maindeck and the sideboard on file, so either new tech or a misread archetype. Only marked against a complete list, because in a partial one absence from the sideboard says nothing.

The block needs no archetype: without one it simply falls to the game-one-only reading, which is why `buildReplaySummaries` takes the entries with a `[]` default rather than being gated like the decklist. On screen and in HTML it is a **sibling** block in amber rather than a second row inside the summary — one is observed, the other inferred, and they should not read as one list.

**Tokens are excluded** via `CardRecord.isToken`: a Treasure the opponent made is not a card in their deck, and this list is about the deck.

### The matchup decklist in a replay

Below the match summary sits the opponent's list **as it stands on file** — `opponentEntries` grouped by type, then Sideboard, then the net Also Seen delta. The seen summary answers "what did they have"; this answers "what else do they have", and against a 75-card list the gap is most of it. Pushing a match into Also Seen grows this block, which is the loop closing.

**Collapsed by default**, with the counts (`60 main · 15 sideboard · 8 also seen`) always on the header. A replay is opened to read the narration, and a full decklist above it would push that down the screen on every visit — but a list on file should never be invisible either.

**Cards seen this match are tinted** (`.is-seen`), since an unmarked list sitting beside a seen list only invites doing that comparison by eye. Both sides go through `normalizeCardName`, because MTGA's spelling of a name need not match the database's.

It shares the match summary's `showSummary` toggle and the push's archetype gate — the archetype is what says *which* matchup's list this is — and orders through the same `groupEntriesByType` / `sortEntriesForExport` as the Plans panel and the exports, so no two lists of the same cards can come out in a different order. The seen map is computed **once** in `ReplayView` and handed to both the summary and the decklist, so the two cannot disagree about what was seen.

`ReplayCardName` takes a `className` and keeps it even on the no-image path, so a marked card the database does not know still reads as marked rather than silently losing it.

**The decklist travels with the exports too**, under the same toggle and the same archetype gate, and in the header region of either scope rather than per game — it is reference for the whole match. `buildReplayDecklist` prepares it once in `ReplayView` as plain data (`{ label, counts, sections }`), which both the on-screen block and the two exporters render. It is built in `App.tsx` because the type grouping lives there, and crosses over as data so the exporters keep knowing nothing about decks.

The text form is a plain indented outline; the HTML form keeps the tab's heading-column layout with working hover previews, since that file is the one meant to look like the app.

### Pushing into Also Seen

A **To Also Seen** button beside To Journal sends every card the opponent was seen to hold across the match into that matchup's `opponentVariantEntries` — the durable archetype knowledge the Plans tab reads, built from a game actually played rather than typed in by hand.

**It is gated on the opponent being categorised.** Also Seen belongs to a matchup, and the archetype in `replayOpponents` is the only thing that says *which* matchup these cards describe; uncategorised, there is nowhere to put them, so the button is disabled and says why. An archetype that is no longer a current matchup (renamed or deleted) is reported distinctly from one never set.

**`applyVariantEntries` is the one definition of writing Also Seen**, shared with the Opponent Deck panel: clamp to four copies, recompute the matchup's colours from the net delta, store. It reads the matchup from the updater's own argument instead of closing over one, which is what lets a caller outside `PlanEditor` use it with nothing but an id. Without sharing it, a card arriving from a parsed game would be stored on different terms from one typed in — the colour recompute in particular was easy to forget.

**Pushing twice is a no-op, not a doubling.** `mergeVariantEntries` keeps the higher count per card, and the counts pushed are the per-game maximum `observedOpponentCards` already computes — the same rule Also Seen merges on, so the two agree by construction. The merge runs *inside* the updater against `item.opponentVariantEntries`, never a copy read outside it.

Tokens are excluded, as in the summary. A name the synced database does not know **cannot** become an entry at all, since an entry carries a card id — those are counted and named in the report line rather than silently dropped, since a systematic mismatch between MTGA's names and Scryfall's is worth seeing.

### Importing into the Journal

Two entry points, one direction of data. The Replay tab's **To Journal** button adds the selected match; the Journal's **Import from Replay (N)** button adds every parsed match for that deck not already there. `matchLogFromReplay` builds the entry and `addMatchLogs` merges it newest-first.

**Duplicates are impossible by construction.** `MatchLog.replayMatchId` records the MTGA `matchID`, and `replayMatchesToImport` filters against it, so the same match cannot arrive twice from either side. The Replay button reads `In Journal` and is disabled once imported, rather than silently doing nothing on a press. A match with no `matchID` is never offered, since it could not be deduplicated.

**Notes arrive pre-filled with the two prompts the log can answer**, numbered to match `JOURNAL_NOTES_PROMPTS` rather than by position — `Q1. What did you board in/out?` and `Q2. What did you see them board in?`:

```
1: IN: Dawn's Truce; Get Lost; 2 Origin of Metalbending; 3 Seam Rip
OUT: 2 Bejeweled Warg; 2 Llanowar Elves; 3 Tender Wildguide
2: Possibly boarded in: Flow State; Glacierwood Siege; Sleight of Hand; Stock Up
```

Because the numbering is the prompt's, **`2:` keeps its number when `1:` is switched off**, and line 1 is omitted entirely rather than renumbered. `OUT:` sits on its own line without a number: a sideboard plan reads as a pair, and running both halves together makes neither scannable. Game one gets blank notes, having no boarding of either kind. Every other prompt is left for the player — the replay records what happened, the journal is for what you thought about it.

Line 1 follows the **My sideboarding** toggle, so an imported note carries exactly what the tab was showing. The Journal's own import button has no such toggle and passes `true`, matching the Replay tab's default.

`gameNotesFromReplay` lives in `replayExport.ts` beside `boardedIn`, which it calls — that is also why `boardedIn` is exported. It needs `cardByName` (the opponent read drops tokens and lands, which it cannot do without knowing what a card is), so `JournalView` now takes the index, and the **popped-out Journal window builds its own** from `loadCardDatabase()` since it has no workspace around it.

What else carries over: the archetype from `replayOpponents` (blank when uncategorised — the journal's opponent field is a matchup picker, and an MTGA screen name is not a matchup), the date, each game's result, and **play/draw stored explicitly** rather than left to `inferGameStart`, since the log actually knows. Notes carry only the two pre-filled answers described above.

The Journal loads its own copy of the parsed matches rather than receiving them from the workspace, so the **popped-out Journal window** can import too.

**Known limitation — the date is the archive file's mtime** (`playedAt: entry.modifiedAt`), not the match's own time. It is right for a freshly swept log, but every match inside one archive shares it, so two matches from one MTGA session get the same date and a long-lived log reports its last write. Fixing it means finding a wall-clock timestamp in the log itself.

### Categorising the opponent

- The **Opponent deck** dropdown writes `Deck.replayOpponents[matchID]`. Once set, the descriptor reads `vs LazyPunda's Simic Mill` everywhere — match picker, body header, and the `Opponent:` line of both exports — via one `opponentLabel()` helper so the same match cannot be described three ways.
- **`guessArchetype`** scores cards the opponent was *seen to own* against each matchup's `opponentEntries` + `opponentVariantEntries`, using the same `containment` as deck attribution. **No threshold** — it always offers its best candidate with a score, since the dropdown overrides in one click. It is a suggestion, never an assignment: nothing is written until clicked, so opening the tab cannot quietly edit the deck. Measured: a deck genuinely absent from the saved matchups scored 0.22, decks on file scored 1.00 from as few as ten cards.
- Mill events are excluded from "seen to own" by the seat filter alone, since a mill line is attributed to the card's **owner** (whoever is being milled).

### Export

Per scope: **Copy** puts plain text on the clipboard, **Download** writes HTML (`replayHtml.ts`) with colours, per-kind styling and working card previews. There is deliberately **no `.txt` download** — Copy already gives the text, so a text file would only be the same words with less in them.

**The HTML is standalone and script-free.** Hover previews are pure CSS (`.c:hover .p`), so nothing has to run. Card images stay as **Scryfall URLs rather than embedded data**: inlining them would take a ~20KB file into the tens of megabytes, and the app already loads previews from those same URLs. The consequence is that images need a connection; the narration itself reads fine offline. The app positions previews with JS so they can flip sides near a window edge — a static file cannot, so the preview is anchored below-right and allowed to clip at the extreme edge rather than shipping a script for it. Card names are wrapped from the event's own `cards`/`card` fields, the same rule the on-screen `ReplayText` uses, so no stray word in the prose becomes a link. Every piece of text is escaped.

The optional blocks travel in a **`ReplayExtras` bag** (`summaries`, `decklist`, `boarding`) rather than as more positional arguments: there are three, all optional, and a caller passing them in the wrong order would type-check silently.

`buildReplayText(match, game?, archetype?)` backs both scopes, differing only in which games it is handed, so match and per-game exports cannot drift. A per-game file still carries the match header plus `This file: game 1 of 2`. The match record is **counted** from game results rather than derived as "games minus wins", so an abandoned game reads as no-result instead of a loss. Opponent names are scrubbed before reaching a filename.

### Bulk export: every match against one archetype

An **All vs <archetype> (N)** button in the replay bar zips one HTML file per match played against the archetype currently assigned. Deck-scoped, like the rest of the tab. It appears whenever an archetype is assigned, **including for a single match**: hiding it below two would mean having to know how many matches are on file before knowing whether the control exists, when the count on the button is how you find that out.

Each match gets its **own** summaries, since they describe what happened in that match; the decklist is shared, being a property of the archetype rather than of any one game. Both still follow the toggles, so a zip carries what the tab was showing.

`src/zip.ts` is a **hand-written ZIP writer, deliberately not a dependency** — the reason recorded against tesseract above: every runtime dependency is another thing that works in dev and dies in a packaged `.exe`. It is ~120 lines with no imports.

- **Stored, not deflated** (method 0). Compression would need either a third-party deflate or `CompressionStream`, and so a fallback path that can only be exercised on some machines; these are tens of kilobytes going to local disk, so the saving is not worth a branch. Verified to open in Python's `zipfile` (CRC-checked) and in Windows' own `Expand-Archive`.
- **Filenames are deduped** by `uniqueNames`. Two matches on one day against one opponent produce the same name, and a zip holding duplicate names cannot be fully extracted. Confirmed against real data: two same-day matches became `…-vs-LazyPunda.html` and `…-vs-LazyPunda-2.html`.
- Flag bit 11 marks filenames as UTF-8, because player and matchup names reach them.
- `concat` and `record` allocate from an explicit `ArrayBuffer` so they return `Uint8Array<ArrayBuffer>`. `TextEncoder.encode` returns the looser `<ArrayBufferLike>`, which spreads through anything built from it and is then rejected as a `BlobPart`.

### Shared scoring and packaging

`electron/cardMatching.cjs` holds `containment` / `countByName` / basics weighting, used by both the main process and the renderer. It lives under `electron/` **for a packaging reason**: electron-builder ships `dist/**/*` and `electron/**/*`, so a top-level `shared/` folder would build, lint and run in dev, then die in a packaged `.exe` — the same failure shape as the `tesseract.js-core` packaging bug described under Screenshot OCR import. It is CommonJS because the main process ships unbundled and `require`s it directly; `cardMatching.d.cts` gives the TypeScript side real types. Vite bundles the renderer's copy into `dist/`.
